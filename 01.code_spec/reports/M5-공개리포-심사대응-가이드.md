# M5 · 공개 리포 가이드 — 심사자가 실제로 확인하는 것과 지금 무엇이 걸리는가

> **작성 2026-08-19 · 근거는 전부 실행된 명령의 출력이다(§1-1).** 대상은
> `github.com/arkwith7/sdkb-dataset`(HEAD `03b2d1a`)이고, 대조 기준은 투고 파생본
> [manuscript.md](../../paper/submission/manuscript.md) §6.6 이다. **판정·수치 변경 0.**

## 0. 한 문장

**자원(C1) 쪽 공개는 이미 심사에 내놓을 수준이지만, 논문이 인용하는 서명이 공개 리포에서
해결되지 않고 평가 자산이 통째로 비어 있어, 지금 상태로는 §6.6 의 약속이 문서로만 존재한다.**

## 1. 심사자가 하는 세 가지 확인과 현재 결과

### ① 논문이 명시한 서명을 찾는다 — **실패**

§6.6 은 *"본 논문이 사용한 것은 상류 스냅샷 `d578bf3` 에 대응하는 고정 릴리스"* 라고 쓴다.
그러나 공개 리포에서 그 커밋은 존재하지 않는다.

```
$ git cat-file -t d578bf3    # sdkb-dataset
fatal: Not a valid object name d578bf3
```

원인은 **서명의 이름공간이 다르기 때문**이다. 스냅샷 `PROVENANCE.json` 의 `source_repo` 는
`github.com/arkwith7/semiconductor-knowledge-base.git`(비공개)이고, 공개 리포는
`sdkb-dataset` 이다. 즉 논문은 **심사자가 볼 수 없는 리포의 커밋 해시**를 재현 기준으로 제시한다.
이것이 이 문서에서 가장 무거운 결손이다 — 재현성 주장 전체가 이 한 줄에 걸린다.

### ② §6.6 가용성 목록을 대조한다 — **셋 중 하나가 통째로 빈다**

| §6.6 항목 | 공개 리포의 상태 | 판정 |
|---|---|---|
| 공유 T-Box · SHACL · CQ 스위트 | `ontology/` 13 TTL · `validation/` shapes 3 · `queries/cq/` **31** | **충족** |
| 자동 계수 보고서 · provenance | `data/reports/` **20건** · `provenance/` 2건 | **충족** |
| 전문가 매칭 A-Box · 규제 인스턴스 | `sdkb-abox-experts-problems.ttl` · governance 4종 | **충족** |
| 재인출로 대체(특허 A-Box 등) | 수집·조립 스크립트 실재 · README 가 33,934 대 33,931(0.009 %) 보고 | **충족** |
| **평가 자산 전량** | qrel·분할 식별자 **없음** · 동결 임계 **없음** · 게이트/누출 규칙 **없음** · 결함주입 명세 **없음** · 결과표 원본 **없음** · 그림 생성 코드 **없음** · T4 계측기 **없음** · 실패 유형 코딩 규약 **없음** | **전무** |
| supplementary S1·S2·S3·S5·S6 | **없음** (원고는 S5 만 **23회** 인용한다) | **전무** |
| 미공개 사유 | *"평가 하네스 저장소는 공개할 경우 봉인 규율이 무효화된다"* | **자기모순** — 봉인은 개봉 완료이고, 같은 절이 qrel 식별자를 공개 대상으로 이미 선언한다 |

### ③ 인용 방법을 찾는다 — **고정점이 없다**

- **태그 0개**(`git tag` 무출력) · GitHub 릴리스 없음 · DOI 없음.
- `CITATION.cff` 의 `version: "1.0.0-dev"` · `date-released: "2026-05-12"` — 논문 실험보다 앞선
  날짜이고, `-dev` 는 **고정 릴리스가 아니라는 선언**이다.
- 그 결과 §6.6 의 *"고정 릴리스"* 를 가리킬 대상이 리포에 존재하지 않는다.

**부수 관측 하나 — 작동하는 기제도 있다.** `provenance/PROVENANCE.json` 의 자산 해시는 실제로
맞는다(`concept_mapping.json` sha256 `cdf5fa5d…` 가 논문 스냅샷 사본과 **일치**). 문제는 그
파일이 **자산 1건만** 등재한다는 것이다 — 기제는 옳고 적용 범위가 좁다.

## 2. 무엇을 어떻게 가져갈 것인가 — 다섯 결정

### D1 · 서명의 이름공간을 공개 쪽으로 옮긴다 (최우선)

논문이 인용할 기준은 **비공개 상류 커밋이 아니라 공개 리포의 태그**여야 한다.

1. 논문 실험에 대응하는 상태로 `v1.1-paper` 태그를 끊는다.
2. `provenance/PROVENANCE.json` 을 **전 자산 등재**로 확장한다(현재 1건 → TTL 13 + shapes 3 +
   CQ 31 + mappings + reports). 등재 형식은 이미 옳으므로 **범위만 넓힌다.**
3. 그 태그에 Zenodo DOI 를 붙인다. 편집자가 데이터 가용성 진술에서 **DOI 를 먼저 본다.**
4. 상류 커밋 `d578bf3` 는 **삭제하지 않고 대응표로 남긴다** — 감사 추적성은 우리 규약이고
   (§0.9), 심사자가 쓰는 것은 공개 태그다.

### D2 · 두 문 구조를 README 최상단에 만든다

지금 README 는 데이터셋 소개로 시작해 재현자가 자기 자리를 찾지 못한다. 첫 화면에 갈림길을 둔다.

```
데이터셋을 쓰려면      → §Setup · uv sync
논문 결과를 재현하려면 → benchmark/README.md · uv sync --extra benchmark
```

### D3 · 평가 자산과 하네스를 `benchmark/` 하위 트리로 싣는다

허용목록·라이선스·의존성 분리는 [PLAN-058](../plans/PLAN-058-single-repo-benchmark-release.md)이
이미 확정했다. 이 문서는 **왜 그것이 심사에 필요한가**만 더한다 — §4 표 4는 일곱 구성 각각에
코드 진입점을 적어 두었고, 그 표가 가리키는 파일이 없으면 표 자체가 **검증 불가능한 주장**이 된다.

### D4 · supplementary 5종에 공개 도달 경로를 준다

S5 는 본문이 23회 인용한다. 투고 시 supplementary 로 함께 제출하더라도, **공개 리포에 사본을
두면 편집자가 링크 하나로 도달**한다. `benchmark/supplementary/` 에 둔다.

### D5 · 알려진 결손을 리포가 먼저 말하게 한다

§4.5 가 자인한 결손 둘(세대 차이로 인한 개념 링크 불일치 · 하이브리드 산출물의 바이트 비재현)을
`benchmark/README.md` 최상단에 싣는다. **재현자가 먼저 부딪히고 나중에 발견하는 것과, 리포가
먼저 밝히는 것은 심사에서 다르게 읽힌다.**

## 4. 원고 쪽 동반 수정 (판정·수치 변경 0)

1. §6.6 의 스냅샷 인용을 **공개 태그 + DOI** 로 바꾸고, 상류 커밋은 대응표 참조로 내린다.
2. §6.6 "미공개와 사유"에서 하네스 항목을 빼고 공개 목록에 넣는다.
3. §4.3 표 4의 코드 경로를 공개 트리 기준으로 한정한다.
4. 셋 모두 `make verdicts` · `submission-check` · `style-check` 를 통과해야 한다.

## 5. 하지 않는 것

- **수치를 다시 산출하지 않는다.** 이 문서의 작업은 전부 공개·배치·문구이며 실험이 아니다.
- **공개를 위해 결손을 지우지 않는다.** 결손은 명시하되 은폐하지 않는다(§8 보고 방식).
- **README 의 계수를 손으로 고치지 않는다.** 계수는 생성기 산출물에서 온다(§1-7).
