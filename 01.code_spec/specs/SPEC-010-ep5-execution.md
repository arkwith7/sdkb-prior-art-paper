## 0. 결론 먼저

**A-4 는 "선행 조건 둘을 채우면 도는 실행"이 아니다. 실행기가 없고, 게이트 두 층이 이 자원에서
현행 형태로는 판정을 낼 수 없다.**

- **없는 것 넷** — D₀…D₅ 조립기 · 정상 델타 생성기(합성 30) · 이행 조건 R/N 적용기 ·
  EP5 드라이버(결함 21 + 정상 31 + 계보 ≤10 · τ 격자 · McNemar · 비용표).
- **막힌 것 둘** — **L2 는 예외로 죽고**(owlready2 metaclass 충돌), **L1 은 무결한 그래프에서도
  위반 293건**을 낸다. 둘 다 판정 이전에 결정해야 하는 **계측기 문제**이며, 결과를 본 뒤
  고치면 그 순간 사후 조정이다(§1-3).
- **도는 것 하나** — A-1 이 깐 배선은 실제로 돈다. 개발 그래프에서 CQ 15개가 1.3 초에 돌아
  15/15 통과했고, 트리플 수 53,871 은 사전등록 §3 의 기재와 일치한다.

**결정이 필요한 자리는 둘이고**(§4), 그 둘이 결정되기 전에는 구현을 시작하지 않는다.

## 2. 분석 — 실측 (2026-08-22)

측정은 전부 **개발 자원**에서 했다. 홀드아웃은 파싱하지 않았다.

### 2.1 도는 것 — A-1 배선

개발 그래프 D₀ᵈᵉᵛ = Brick v1.3.0 + 개발 A-Box 2 = **53,871 트리플**(사전등록 §3 기재와 일치).
`run_cqs(profile=brick)` 이 **1.3 초**에 CQ 15개를 돌려 **15/15 통과** ·
스위트별 `fdd 5/5 · space 5/5 · core 5/5`. 술어 추출·헤더 파싱·τ 값이 전부 프로파일에서 나온다.

### 2.2 막힌 것 ① — L2 가 Brick 그래프에서 예외로 죽는다

`reasoner_gate.check_consistency()` 가 `owlready2` 적재 중
`TypeError: metaclass conflict` 로 중단된다. 이것은 "비일관"이 아니라 **판정 불능**이며,
현행 `run_instance()` 는 이 예외를 잡지 않으므로 인스턴스 전량이 실패한다.
사전등록 §6.2 의 `Accept_partial = 1[L0–L3] · 1[T3]` 은 L2 가 도는 것을 전제한다.

### 2.3 막힌 것 ② — L1 이 무결한 그래프에서도 위반을 낸다

| 데이터 그래프 | shape 원천 | 결과 |
|---|---|---|
| D₀ᵈᵉᵛ (T-Box v1.3.0) | 프로파일 고정 `Brick-v1.4.4.ttl` | 위반 **52** (38 = `bsh:hasQUDTReferenceShape`) |
| D₅ᵈᵉᵛ (T-Box v1.4.4) | 같은 판(v1.4.4) | `sh:Violation` **293** · `sh:Warning` 147 |

즉 **버전을 맞춰도 Brick 의 공식 예제 A-Box 는 Brick 자신의 shape 을 통과하지 않는다.**
`allow_warnings=True` 로도 통과하지 않는다(위반이 Violation 등급이다). 원인은 둘로 보인다 —
프로파일이 shape 원천을 **v1.4.4 한 판으로 고정**해 계보의 다른 칸과 어긋나는 것(첫 행),
그리고 배포 TTL 이 `owl:imports` 로만 가리키는 외부 어휘(QUDT 등 8건)가 데이터 그래프에
없는 것이다.

**또한 `queries/brick/shapes/delta.ttl` 은 그래프 전체에 걸 수 없다.** S-D1·S-D3 의 대상이
`sh:targetClass owl:Class` · `owl:ObjectProperty` 이므로 D_n 에 걸면 **Brick 의 모든 클래스**가
심사 대상이 된다. 이 shape 은 **델타 그래프**(새 T-Box − 옛 T-Box)에 걸도록 설계된 것이며,
그 델타 그래프를 만드는 코드가 아직 없다. **델타에 걸었을 때의 결과는 확증 판정(§6.2)이므로
이 문서는 측정하지 않았다.**

### 2.4 (N) 이행 조건의 재료 — 기계 적용 가능한 규칙은 2건뿐이다

v1.4.4 실측: `owl:deprecated true` **246건**(Brick 네임스페이스 223 · REC 23) 가운데
**243건이 자연어 `deprecationMitigationMessage` 만** 갖고, SPARQL CONSTRUCT 인
`deprecationMitigationRule` 은 **2건**뿐이며 그것도 폐기 항목이 아니라 `brick:deprecation`
노드 아래 붙어 있다(`powerComplexity`·`powerFlow`). 기계 적용 가능한 이행 재료는 사실상
**`brick:aliasOf` 105건 + `owl:equivalentClass` 210건**이다.

개발 A-Box 가 실제로 쓰는 폐기 항목은 **9건**이고 그중 alias/equivalent 매핑이 있는 것은
**`Floor → Storey` 하나**다. 나머지 여덟(`Building`·`Room`·`HVAC_Zone`·`Temperature` 등)은
**대체 항목 없이 폐기**돼 있다. 이 여덟은 `space`·`core` CQ 와 X2 결함의 `type_pairs`
(Building–Floor · Floor–Room)가 딛고 선 어휘와 정확히 겹친다.

### 2.5 없는 것 넷

| | 산출물 | 현 상태 |
|---|---|---|
| G1 | D₀…D₅ 조립기 (T-Box_n + 홀드아웃 A-Box) | 없음 · `graph_default: null` 로 인자를 기다린다 |

**있는 것은 인스턴스 실행기다** — `analysis/faults.run_instance(profile=…, graph=…,

### 2.6 사전등록이 정하지 않은 자리 둘

- **결함주입의 기저 그래프.** §4.2 는 *"홀드아웃의 `brick:hasPart`"* 라고만 적고 **어느 T-Box
  판 위인지** 말하지 않는다. `GEN=d0` 로 기준 세대를 동결한다는 인계와 T3 가 d0 대비 회귀를
  본다는 사실을 합치면 **D₀(v1.3.0 + 홀드아웃)** 가 자연스러운 독법이다.
- **`D0` 라벨의 이중 사용.** §1.1 의 D₀ 는 *T-Box + **홀드아웃***, §3 의 D₀ 는 *T-Box + **개발
  A-Box** (53,871)* 다. 같은 기호가 둘을 가리킨다 — 코드에서는 `D0` / `D0_dev` 로 갈라 적고,

**둘 다 결과 확인 이전에 정하고 사유를 남긴다.** 지금 정하는 것은 사후 조정이 아니다.

| | 쟁점 | 선택지 | 이 문서의 권고 |
|---|---|---|---|
| **①** | **L2 판정 불능**(§2.2) | (a) 적재기를 고쳐 살린다 (b) `L2 = null` 로 기록하고 부분 승인식에서 뺀다 | **(a) 를 먼저 시도하고, 실패하면 (b)** — 층을 빼는 것은 검출력 감소이므로 근거를 남긴다. (b) 로 가면 `Accept_partial` 정의가 `1[L0·L1·L3]·1[T3]` 로 바뀌며 **그것은 사전등록 §6.2 의 해석 변경**이라 별도 승인이 필요하다 |

## 6. 설계 — 승인된 결정의 기록 (2026-08-22)

**§3 의 권고 다섯과 §4 의 결정 둘이 승인되었다.** 아래는 그 결정을 코드가 읽을 수 있는 형태로
좁힌 것이며, **결과를 보기 전에 적는다.**

### 6.1 결정 ① · L2 는 살린다 — OWL Full → DL 사영 규칙 하나

**원인은 트리플 하나다(실측).** Brick 은 `brick:EntityProperty a owl:Class ; rdfs:subClassOf
owl:ObjectProperty` 를 선언한다. 클래스 계층에 OWL 빌트인을 얹은 **메타모델링**이며 OWL 2 DL
밖이다. HermiT 는 DL 추론기이므로 이 그래프를 원리적으로 받지 못한다 — 즉 이것은 버그가 아니라
**적용 범위의 문제**다.

**규칙(자원 일반).** 추론 뷰에서 `rdfs:subClassOf`·`rdfs:subPropertyOf` 의 목적어가 OWL/RDFS
빌트인(`owl:Class`·`owl:ObjectProperty`·`owl:DatatypeProperty`·`owl:AnnotationProperty`·
`rdf:Property`·`rdfs:Class`·`rdfs:Resource`)인 트리플을 제거한다. 기존 뷰가 이미 하는 일
(`owl:imports` 제거 · `xsd:date`→`dateTime`)과 **같은 층의 사영**이며, 제거 건수를 반환해
보고에 싣는다.

**부작용 없음이 실측으로 확인됐다** — SDKB `graph_v0.ttl` 에서 해당 트리플은 **0건**이므로
사영은 무연산이고 계약 ①(`gate-graph` diff 0)이 보존된다. Brick 개발 그래프에서는 **1건**을
제거한 뒤 HermiT 가 **5초**에 일관 판정을 냈다.

**제거된 트리플은 판정에서 빠진다는 사실을 결과에 적는다.** 결함 X2·X3·X4 는 이 트리플을
건드리지 않으므로 검출력에는 영향이 없다.

### 6.2 결정 ②·③ · L1 은 **자기 판의 shape** 으로 **기준 대비 신규 위반**만 본다

- **shape 원천.** `D_n` 은 자기 T-Box 판이 싣고 있는 SHACL 을 쓴다. 프로파일의
  `shapes_graph` 고정값은 **기본값**으로 남기고, 계보 판정은 판별 인자로 shape 을 받는다.
  옛 그래프를 새 판의 shape 으로 재는 것은 게이트가 아니라 시대착오다.
- **판정 형태.** `conforms` 이진은 **상수**다 — 무결한 D₅ᵈᵉᵛ 에서도 `sh:Violation` 293건이
  나온다(§2.3). 그래서 판정은 **위반 집합의 비회귀**로 한다:

  `L1_fail(new | base) ⟺ V(new) \ V(base) ≠ ∅`

  `V(·)` 는 SHACL 결과 그래프에서 뽑은 `sh:Violation` 등급 결과의 정규화 튜플 집합이며,
  키는 `(sourceShape, focusNode, resultPath, constraintComponent, value)` 다. **텍스트 보고서를
  파싱하지 않는다** — 결과 그래프를 직접 읽는다. `sh:Warning`·`sh:Info` 는 세지 않는다.
- **왜 T3 와 같은 형태인가.** T3 가 행 수 회귀를 보는 이유(절대값이 아니라 **변화**가 회귀의
  정의다)가 L1 에도 그대로 적용된다. 형태를 맞추면 두 층의 판정을 같은 자로 읽을 수 있다.

### 6.3 결정 ④ · 델타 그래프

`Δ(n→n+1) = triples(T-Box_{n+1}) − triples(T-Box_n)`. **공백노드를 담은 트리플은 개수만 세고
집합 연산에서 제외한다** — SPEC-009 §4 각주가 정한 자를 그대로 쓴다(적재마다 라벨이 바뀌므로
차집합이 무의미해진다). 제외 건수는 산출물에 남긴다. `delta.ttl`(S-D1–S-D3)은 **이 델타
그래프에만** 건다.

### 6.4 결정 ⑤ · (N) 이행 조건의 범위

**(R)** 원본 A-Box 를 새 T-Box 에 그대로 얹는다.
**(N)** 아래 순서로 A-Box 의 폐기 항목을 재작성한 뒤 얹는다.
1. `brick:deprecationMitigationRule` 의 SPARQL CONSTRUCT 적용 (실측 **2건**),
2. `brick:aliasOf` (105) · `owl:equivalentClass` (210) 사상으로 폐기 항목 치환.

**(a) 규칙 2건만으로는 R 과 N 이 사실상 같은 조건**이 되어 §6.3 의 비교가 공허해진다. 적용
규칙 전문·적용 건수·치환된 항목 목록을 산출물에 남기고, **매핑이 없어 치환하지 못한 폐기
항목도 개수와 목록으로 남긴다** — 개발 A-Box 기준 폐기 사용 9건 중 매핑이 있는 것은
`Floor → Storey` 하나였다(§2.4).

### 6.5 §2.6 의 미정 둘

## 8. 판정 결과 (2026-08-22 · 각 1회 · 재판정 없음)

### 8.1 결론 먼저

**절차는 이식되었고, 결함 계측기는 이식되지 않았다.** L0–L3 + T3 는 제2 도메인에서 코드 변경
없이 돌았고 정상 델타 30건을 하나도 거부하지 않았다. 그러나 사전등록이 동결한 결함 셋 가운데
**X2 는 홀드아웃에서 후보가 0** 이어서 주입되지 않았고, 판정 가능한 12건에서 **T3 단독 검출은
0** 이다. **DP3 의 등급은 올리지 않는다** — 사전등록 §7 위험표가 예상한 "T3 단독 검출 0" 경로이며,
DP3 의 경험적 도전 조건이 부분 성립했다.

### 8.2 교차 결함 — 21건 중 9건은 판정이 아니다

| 결함 | 인스턴스 | 후보 | 주입 | 판정 |
|---|---|---|---|---|
| X2 공간 포함관계 역전 | 9 | **0** | 0 | **공허** |
| X3 공유 관계 동치 오선언 | 3 | 3 | 1·2·3 | 가능 |
| X4 위치 재배선 | 9 | 10 | 1–2 | 가능 |

`T3 단독 검출 0/12 · 불일치 쌍 0 · 단측 McNemar p = 1.0`. 사전등록 §6.1 이 미리 적은 검정력
한계(불일치 쌍 5건 미만이면 유의 불가)가 그대로 발동한다.

**X2 가 공허한 이유는 자원의 모델링 관습이다(실측).** 동결된 명세는 `brick:hasPart` 의
Building–Floor·Floor–Room 쌍을 대상으로 한다. 홀드아웃 `soda_brick` 의 `hasPart` 243건은
**전량 `HVAC_Zone → Room`** 이고, Building–Floor·Floor–Room 포함관계는 **`isPartOf` 250건**으로
표현된다. 개발 건물 `rice_brick` 은 같은 관계를 `hasPart` 로 써서 후보가 90건이었고 실제로
검출됐다(SPA01 90 → 72 · T3 `space`·`core` 회귀). X4 도 같은 방향이다 — `isLocationOf` 가
홀드아웃에 10건뿐이다(개발 181건).

**이것을 "T3 가 교차 결함을 놓쳤다"로 적지 않는다.** 관측된 것은 **결함 명세가 자원을 건너
이전되지 않는다**는 것이며, 절차의 이식과 계측기의 이식은 다른 문제다.

### 8.3 정상 델타 — 위양성 0/30
