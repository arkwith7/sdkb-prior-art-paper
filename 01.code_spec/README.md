# 01.code_spec — 코드 스펙 · 개선 계획 · 진행 실적

이 디렉터리는 **이 저장소에서 무엇을 만들었고 무엇을 만들 것인가의 정본**이다.
대화 맥락은 사라지지만 이 문서는 남는다 — 새 세션은 여기서 시작한다.

[CLAUDE.md](../CLAUDE.md) 가 *어떻게* 일할지(규약)를 정한다면, 여기는 *무엇을* 하는지(내용)를 담는다.

---

## 무엇을 어디에 쓰는가

| 문서 | 담는 것 | 언제 쓰는가 |
|---|---|---|
| **[STATUS.md](STATUS.md)** | 진행 실적 대시보드. 끝난 것 · 진행 중 · 대기. 근거 수치와 커밋 SHA | 작업이 끝날 때마다 갱신 |

| **[GLOSSARY-STATISTICS.md](GLOSSARY-STATISTICS.md)** | **통계 개념·용어 정의.** 비열등 검정 · 짝지은 부트스트랩 · Holm · McNemar · 전복 문턱 · κ, 그리고 **각 개념에서 실제로 미끄러진 지점** | 판정을 읽거나 쓰기 전. 검정 방법이 바뀌면 갱신 |

| **plans/PLAN-xxx** | **아직 안 한 일의 계획** — CLAUDE.md §2 의 5단계를 담는 틀 | 작업을 시작하기 전 |

| **[TOOLING.md](TOOLING.md)** | **온톨로지 조회·편집·검증 도구의 설치·운영 정본** — Protégé(WSL)·pySHACL·VS Code 확장. 도구로 손댄 뒤의 게이트 회귀 순서 | T-Box/A-Box 를 GUI 로 조회·수정할 때 |
| **[CANONICAL-INDEX.md](CANONICAL-INDEX.md)** | **"지금 무엇이 정본인가"의 최종 판정** — 서명 숫자(§1 · 디스크 정박점과 대조) · 라벨 규약(§0.1 · C·RQ·H·DRQ·DP·EP) · 디렉토리별 분류 | 숫자나 라벨이 문서마다 다를 때 |
| **reports/** | **실험 기록** — 무엇을 어떻게 재서 무엇이 나왔는가(M4 계열) | 결과의 근거를 되짚을 때. **판정의 정본은 원고 §6** |
| **[../upstream/](../upstream/)** | **C0 · 상류 환류** — `DEFECT-LEDGER.md`(결함 D-NN) · `CR-NNN`(변경 요구) · `HANDOFF-QUEUE.md`(송부 순서) | 실험이 **온톨로지 자원의 결함**을 드러냈을 때 |

PLAN 이 완료되면 STATUS 를 갱신하고, 거기서 확정된 계약은 SPEC 으로 **승격**한다.
PLAN 은 지워지지 않는다 — 왜 그렇게 결정했는지의 기록이기 때문이다.
**종결된 PLAN·구 패러다임 문서는 `archive/` 로 내리되 지우지 않는다**(사전등록 증거·커밋 해시 불변).
결론 한 줄 요약은 [CANONICAL-INDEX §3.1](CANONICAL-INDEX.md) 에 모아 둔다 — **원문은 인용 금지**.

## 문서를 쓸 때의 규칙

1. **수치는 실행 출력에서만 가져온다.** 추정치는 "추정"이라고 쓴다. (CLAUDE.md §1.1)
   모든 수치에 **출처 명령**을 병기한다 (`make gate`, `pytest`, 스크립트명).
2. **각 문서는 어느 주장을 지지하는지 첫 줄에 밝힌다.** **C0(상류 환류) / C1(자원) / C2(핵심증명 ·
   선행기술 검색) / C2′(전달) / C3(진화안전 · T-gate) / C4(설계지식)** 중 무엇인가, 그리고 사전등록된
   평가 점검 **H3·H5** 또는 설계 연구질문 **DRQ1–DRQ3′** 중 어느 것인가.
   답할 수 없으면 그 작업은 스코프 밖이다(CLAUDE.md §0).
   **구 라벨 주의 (2026-08-20 개정):** 구 커버리지 H1 · 구 시계열 H2 · 구 이식성 RQ3 은 문맥 없이
   "H1"이라 쓰지 않고 **"구 커버리지 H1" 형식**으로 쓴다. **S-시리즈 재라벨 규약은 폐기됐다** —
   `S1`–`S3` 는 이제 supplementary 파일만 가리킨다(CLAUDE.md §0 말미 ·
   [CANONICAL-INDEX](CANONICAL-INDEX.md) §0.1). 대응 사전은 [RECONCILIATION-v09.md](RECONCILIATION-v09.md) §1.
3. **실패·기각·포기한 선택지를 지운다.** — 지우지 않는다. 왜 그 길을 안 갔는지가 가장 중요한 기록이다.
4. **계약을 바꾸는 코드 변경은 SPEC 을 같은 커밋에서 고친다.** 한쪽만 고치면 문서가 거짓이 된다.

## PLAN 문서의 틀

CLAUDE.md §2 의 5단계를 그대로 따른다. 🛑 는 사용자 승인 없이 넘어갈 수 없다.

```markdown
# PLAN-xxx · <제목>

| | |
|---|---|
| 지지하는 것 | C_ (C0/C1/C2/C2′/C3/C4) / DRQ_ 또는 평가 점검 H3·H5 / 논문 §x.x |
| 상태 | 요구정의 🛑 / 분석 🛑 / 설계 🛑 / 구현 / 검증 🛑 / 완료 |
| 승인 | (사용자가 승인한 날짜와 무엇을) |

## 1. 요구정의  🛑
목적 / 입력 / 출력 / 성공 기준 / 비목표

## 2. 분석  🛑
실제 데이터를 관찰한 **사실**. 가정은 "가정"이라고 라벨링.
여기서 나온 사실이 1단계와 충돌하면 되돌아간다.

## 3. 설계  🛑
어느 모듈에 무슨 함수. 결정적인가. 통계면 검정 방법·단측/양측·효과크기를 **여기서 확정**한다.

## 4. 구현
승인된 범위 안에서만.

## 5. 검증  🛑
실행 출력과 함께. 실패는 실패로.
```

## SPEC 문서의 틀

```markdown
# SPEC-xxx · <제목>

| | |
|---|---|
| 지지하는 것 | C_ (C0/C1/C2/C2′/C3/C4) / DRQ_ 또는 평가 점검 H3·H5 / 논문 §x.x |
| 구현 | src/... , queries/... |
| 검증 | tests/... , make ... |

## 보장하는 것
계약을 하나씩. 각 계약에 그것을 지키는 테스트를 명시.

## 보장하지 않는 것
스코프 방어선. 알려진 한계.

## 왜 이렇게 했는가
기각된 대안과 그 이유.
```
