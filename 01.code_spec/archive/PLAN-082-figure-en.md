## 0. 결론 먼저 — 무엇을 만들고 무엇을 만들지 않는가

**만든다:** 본문 그림 7종의 영문 라벨판을 **같은 그리기 코드에서** 생성하는 경로.
**만들지 않는다:** 새 그림 · 새 수치 · 영문 전용 그리기 코드.

**이 산출물이 지지하는 주장은 없다 — 기존 증거의 언어 렌더링이다.** §0 의 자문
(*"이 산출물은 C0/C1/C2/C3 중 무엇을 지지하는가"*)에 대한 정직한 답은 **"아무것도 새로
지지하지 않는다"** 이다. 그림이 담는 증거는 이미 C1·C2·C3 에 사상돼 있고, 이 작업이 바꾸는
것은 **그 증거를 읽는 사람의 언어**뿐이다. 그러므로 **수치·판정·그림 번호·라벨 기호는 하나도
바뀌지 않는다.**

## 3.5 · 2단계 분석 — 실측이 설계를 바꾼다 (2026-08-26 · 승인 후 수행)

**결론 먼저: 라벨 표만으로는 되지 않는다.** 세 가지가 실측으로 드러났고 셋 다 1단계에서
예상하지 못한 것이다.

### ① 영문은 **1.56배 넓다** — 손으로 정한 상자를 넘친다

`_rbox` 는 **줄바꿈도 잘라내기도 하지 않는다**(실측 · `figures.py:95`). 텍스트는 한 점에
그려지고 넘치면 조용히 상자를 벗어난다. 상자 폭은 한국어 길이에 맞춰 손으로 정해져 있다.

같은 내용의 한국어 라벨과 자연스러운 영문 대응 16쌍의 **렌더 폭**을 실측하였다(정규좌표 ·
실제 폰트 · `_setup_fonts()` 적용).

| | 배율 (영문 폭 ÷ 한국어 폭) |
|---|---|
| 중앙값 | **1.56** |
| 최소 | 0.99 (`승인`→`Accept`) |
| 최대 | **2.64** (`기술예측`→`Technology foresight`) |

**넘침이 실재한다.** 그림 1 의 EP 상자는 폭 `0.178` 인데, 그 안의 부제 *"측정 대상 · A2
절차의 자원 비의존성"*(0.1336)의 영문 대응은 **0.2379** 로 **34 % 초과**한다. 제목
*"EP3 · 통제된 자원 교체"* 도 0.1055 → 0.1855 로 상자를 넘는다.

### ② 라벨의 30 %가 **값을 보간하는 템플릿**이다

한글 리터럴 189개 가운데 **57개가 f-string** 이고 47개가 `\n` 을 품는다. 예:
`f"관찰면 {v['ep5.observable']}/{v['ep5.cq_total']} · 명세 재접지 필요"`.
곧 라벨 표의 항목은 **문자열이 아니라 템플릿**이어야 하며, 그래야 수치가 계속
`concept_values.json` 에서 온다(F6 유지 · 성공기준 G3·G4).

### ③ 그림 3 의 텍스트는 **한국어 supplementary 에서 기계 추출된다**

`fig_tbox_views` 는 `v["views.match"]`·`views.priorart`·`views.foresight` 를 그리는데,
이 셋은 `cast="cells"` 로 **S5 표 3 의 한국어 칸을 통째로** 읽는다(`figdata.py:197`).
영문판에는 추출할 영문 원천이 없다 — **supplementary 는 감사 기록이라 영문화 대상이
아니다**(§8.1).

**그러므로 이 셋만은 "번역"이고, 그 번역은 이미 저장소가 푼 문제와 같은 문제다** —
`build_submission_en.py` 의 `CELLS` 가 표 칸에 대해 하는 일이다(한국어 칸 전체를 키로 하는
완전 일치 치환 + 수치 불변 검사).

## 4. 설계 — 3단계에서 확정할 것 (2단계 실측 반영)

| | 방식 | 장점 | 대가 |
|---|---|---|---|
| **A** | **라벨 표 분리** — `viz/labels.py` 에 `{키: {"ko":…, "en":…}}` 를 두고 그리기 코드는 `L(키, lang)` 으로 읽는다 | 그리기 코드 1벌 유지 · G5 를 표 하나에 걸 수 있다 · 두 언어의 표류가 한 파일에서 보인다 | 리터럴 187개를 키로 옮기는 기계적 작업 |
| **B** | 영문 전용 모듈 복제 | 착수가 빠르다 | **그리기 코드 2벌** — 다음 재측정에서 한쪽만 갱신되어 갈린다. **권고하지 않는다** |
| **C** | SVG 후처리 치환 | 코드 변경 0 | 문자열이 도형에 얹혀 **줄바꿈·정렬이 깨진다** · §1-7 의 취지에 반한다. **권고하지 않는다** |

**권고는 A 다.** 근거는 이 저장소가 이미 같은 문제를 같은 방식으로 풀었다는 것이다 —
`build_submission_en.py` 의 `TERMS`·`CELLS`·`CAPTIONS` 가 표·캡션에 대해 하는 일을, 이
계획은 그림 텍스트에 대해 한다.

**A 에 두 장치를 더한다 — 2단계 실측(§3.5)이 요구한다.**

| | 장치 | 무엇을 막는가 |
|---|---|---|
| **A-1** | 라벨 항목은 **템플릿**이다 — `{ep5.observable}` 같은 자리표시자를 `figdata.load()` 값으로 채운다 | 수치가 코드나 라벨 표에 손으로 적히는 것(F6 · G3·G4) |
| **A-2** | **폭 인식 그리기** — 상자 폭을 아는 `_fit_text()` 를 두어 ⓐ 폭에 맞춰 접고 ⓑ 바닥 크기까지 줄이고 ⓒ **그래도 넘치면 그리지 않고 실패한다** | 영문이 상자를 조용히 넘치는 것(§3.5-①). **넘친 그림을 내보내느니 멈춘다** — 개념 그림이 수치 불일치에서 이미 택한 규율과 같다 |

**A-2 가 이 설계의 방어선이다.** 넘침은 SVG 를 열어 보지 않으면 사람 눈에 띄지 않고,
검사기도 지금은 보지 못한다. 실패시키면 **영문 라벨을 상자에 맞게 쓰도록 강제**된다 —
그것이 규격 F4(그림 글자도 문체·판정 문구 규율의 대상)의 집행이기도 하다.

**그림 3 의 세 칸은 `CELLS` 방식으로 잇는다** — 한국어 칸 전체를 키로 하는 완전 일치 치환.
가능하면 `build_submission_en.py` 의 `CELLS` 를 **공유**하여 같은 칸이 표와 그림에서 다르게
번역되는 일을 원천 차단한다(3단계에서 공유 가능 여부를 확인한다).

**출력 경로도 3단계에서 확정한다.** 후보는 `paper/figures/en/<같은 이름>.svg` 이며, 그러면
`build_submission_en.py` 가 `../../figures/X.svg` → `../../figures/en/X.svg` 로 바꾼다 —
**깊이 보정과 같은 자리이고 같은 이유다**(사람이 경로를 손으로 적지 않는다).

| `viz/figures.py` | `_fit_size()`·`_fit_text()`·`TextOverflow` 신설(A-2) · `_rbox` 가 제목·본문에 폭을 건다 · `--lang` |

| `Makefile` | `make figures-en` 신설 |
| 테스트 **신설 둘** | `test_figure_labels.py`(라벨 계약 · 162건) · `test_figure_outputs.py`(산출물 계약 · 15건) |

### 7.2 구현이 설계를 한 자리 고쳤다 — 넘침 검사의 발동 조건

설계 ②는 *"접기 → 축소 → 실패"* 를 모든 언어에 걸 계획이었다. 구현에서 걸어 보니
**한국어판 그림 4 의 해시가 바뀌었다** — 한국어판에는 선언한 폭을 넘겨 그리는 자리가 이미
있고, 거기에 축소가 걸려 글자 크기가 줄었기 때문이다.

**그래서 검사를 비-한국어에서만 발동시킨다.** 한국어판은 **눈으로 검수를 마친 동결
기준선**이고 그 기하는 이 작업의 대상이 아니다(§5 비목표). 이 장치가 지키는 것은
*"새로 들어오는 언어가 기준선의 기하 안에 머무는 것"* 이다. 상자가 없는 자리에서는
**한국어판이 그 자리에서 실제로 쓰는 폭**을 경계로 삼는다(`_ko_width()`).

**검사는 실제로 일했다** — 첫 영문 생성에서 넘침 **3건**을 잡아 그리기를 거부했다.
