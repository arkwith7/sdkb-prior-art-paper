## 0. 결론 먼저 — 기존 스크립트로는 §3을 집행할 수 없다

PLAN-031 §1은 수집 도구로 `~/Dev/paper_data/scripts/expand_dataset_via_api.py`(3,153줄)를 지정했다.
**그 지정은 유효하지만, 그대로는 §3을 만족시키지 못한다.** 실측(§2)에서 세 가지가 확인됐다.

| §3 요구 | 기존 스크립트 | 판정 |
|---|---|---|
| 표집 순서 = `(출원일, 출원번호)` 오름차순 | **없음.** 전략(stage 1–4)·키워드 게이트 순으로 페이지를 훑는다 | **미구현** |
| IPC 주분류 ∈ 동결 21종 | `ipcNumber`는 **검색식의 필드**일 뿐 주분류 필터가 아니다 | **미구현** |
| 기존 1,000건과 패밀리 서로소 | `seen`은 **출원번호 집합**뿐. 패밀리 개념 없음(`process_family`는 공정 라벨) | **미구현** |
| 거절 · 인용≥1 · claim1 | 사전/사후 필터로 **구현돼 있음**(`examinerQuotationFlag='Y'` · `claimInfoArray`) | 재사용 |
| 호출 1회로 IPC+claim1+인용 동시 취득 | `getBibliographyDetailInfoSearch` 1콜 — **구현돼 있음** | 재사용 |

**따라서 요구는 "스크립트 실행"이 아니라 "§3 집행 드라이버 신설 + 기존 스크립트의 호출·파싱 계층

## 2. 분석 — 실측된 사실 (CLAUDE §2-2 · 가정은 "가정"으로 라벨)

### 2.1 API 키 프로필 — **paid 급으로 확정. free 아님**

| 증거 | 값 |
|---|---|
| `paper_data/data/processed/collect_phase_b_kr.log` 말미 | `used={'kr': 3470, ...} quota_hit=False` |
| `paper_data/data/processed/backfill_admin_docs.log` 말미 | `used=693, quota_hit=False` (예산 캡 800) |
| 스크립트 프로필 정의(`expand_dataset_via_api.py:95`) | free = 150/일 · paid = 600/일 |

**단일 실행에서 3,470콜이 quota 오류 없이 완주**했으므로 이 키는 150/일 플랜이 아니다.
→ **파일럿 500콜은 하루 안에 소화된다.** 다만 이는 *과거 관측*이고 계약 잔여량의 증거는 아니다 —
파일럿 실행 시 `quota_hit` 을 로그에 남겨 **당일 실측으로 재확인**한다(가정 아님, 관측으로 승격).

### 2.2 배제기준 1(패밀리 서로소)의 집행 경로 — **`family_pub_numbers`를 쓰면 안 된다**

PLAN-031 §3 배제 1은 "`family_pub_numbers` 또는 `simple_family_id` 교집합"이라 적었으나, 실측:

- `rejected_patents_meta.parquet`(1,000행 38열)에 **`simple_family_id` 열은 없다.**
- `family_pub_numbers`는 str이며 내용이 **우선권·PCT 출원번호**다 — 예: `PCT/US2021/019245|62/982,956`.
  DOCDB 패밀리 공개번호가 아니다. 토큰 1,411개 중 고유 1,270개 · 보유 행당 평균 2.64개.
- **`has_family = False`가 466/1,000 (46.6 %)** — 절반 가까이가 이 열로는 비교조차 되지 않는다.

**따라서 이 열로 §3 배제 1을 집행하면 기준이 절반만 작동한다.** 대신 이미 있는 정본 경로를 쓴다:
`collect/bq_family_ir`(BigQuery DOCDB) — IR 코퍼스 40,552 문서 **결측 0**, 조인율 **95.8 %**
(docdb-app 89.2 % · docdb-pub 6.6 % · fallback-self 4.2 % = 자기 자신을 패밀리로)
(`data/profiles/ir_family_map.md`).

> **이것은 사전등록의 변경이 아니라 결함의 정정이다.** §3의 *규칙*("기존 1,000건과 동일 패밀리 배제")은
> 그대로이고, 규칙이 지목한 *필드*가 그 규칙을 담고 있지 않았을 뿐이다. 규칙을 느슨하게 만드는
> 방향이 아니라 **더 엄격하게 집행하는** 방향의 정정이므로 §1-2에 저촉되지 않는다.
> 승인되면 PLAN-031 §3 배제 1의 문구를 "DOCDB simple family(`bq_family_ir`) 교집합 ≠ ∅"로
> 정정하고, **정정 사실과 사유를 §8에 남긴다.**
> **미결:** fallback-self 4.2 %는 패밀리 판정 불능이다. 이 건들을 ⓐ 보수적으로 배제할지
> ⓑ 출원번호 일치만으로 판정할지 **개봉 전에 정해야 한다**(§3 설계 단계 결정 사항).

### 2.5 2단계 실측 — §2.4의 세 미확인 항목이 **전부 해소됐다** (2026-07-31)

프로브 3본 · **검색 호출 81콜 소모**(`getAdvancedSearch`). §1 호출 회계대로 **파일럿 500콜(서지상세)과
별도 계정**이다. 스크립트는 scratchpad에 있고, 확정 로직은 3단계 승인 후 `src/`로 승격한다.

#### (1) 서버측 정렬 — **지원된다. 최대 미해결 위험 해소**

| 관측 | 값 |
|---|---|
| `sortSpec=AD` + `descSort=false` | **출원일 오름차순으로 정렬돼 반환**. H01L 1페이지 선두 = `19551230/1019550000655` → `19691...` → … → 말미 `19821115` |
| `descSort=true` 대조 | 내림차순 정상(선두 `20231101`) — 파라미터가 실제로 먹는다 |
| 동일 요청 2회 | **키 순서 완전 동일**(`repeat_identical=true`) |
| 페이지 1↔2 | **중복 0건** · 경계 단조(1페이지 말미 `19821115` ≤ 2페이지 선두 `19830714`) |

→ "앞에서부터"를 **수집 시점 검색 결과 집합에 의존하지 않고** 서버 정렬로 집행할 수 있다.
**남은 결정성 구멍은 하나뿐이다:** `sortSpec`은 단일 필드이므로 **동일 출원일 내부 순서는 서버 정의**다
(관측: 60건 표본에서 최대 타이 블록 3건). §3의 2차키(출원번호)는 클라이언트가 걸어야 한다 → 3단계 결정 A.

#### (2) 출원일 범위 필터 — **`applicationDate=YYYYMMDD~YYYYMMDD` 지원**

| 표기 | 결과 |
|---|---|
| `20050101~20251231` (물결) | **`resultCode=00` · B81B 2,143 → 1,781** · 선두 `20050114` | 
| `20050101\|20251231` (파이프) | `INVALID_REQUEST_PARAMETER_ERROR` |
| `2005~2025` (연도만) | `INVALID_REQUEST_PARAMETER_ERROR` |

→ §3 포함기준 5(2005–2025)를 **서버측에서** 건다. 오름차순으로 1955년부터 훑어 2005에 도달하는
낭비가 사라진다. **`numOfRows` 상한은 500**(1000 요청 시 500 반환) · 깊은 페이지(`pageNo=15`) 정상.

#### (3) 검색 응답이 **주분류와 등록상태를 이미 싣고 있다** — 예산 구조가 바뀐다

응답 필드 16종: `applicationNumber` · `applicationDate` · **`ipcNumber`**(전체 목록 · 파이프 구분 ·
선두가 주분류 · 예 `H10B 69/00|H01L 21/8247|B82Y 10/00`) · **`registerStatus`** · `astrtCont`(초록 전문) ·
`inventionTitle` · `applicantName` · `openNumber`/`openDate` · `registerNumber`/`registerDate` ·
`publicationNumber`/`publicationDate` · `indexNo` · `drawing`/`bigDrawing`.

→ **§3의 포함 1(거절)·4(IPC 주분류)·5(출원일)와 배제 1·2(패밀리·출원번호)를 서지상세 호출 없이**
검색 응답만으로 판정할 수 있다. 서지상세 콜은 **남은 두 조건(인용 ≥ 1 · claim1 전문)** 에만 쓴다.
이는 §3의 기준을 바꾸지 않고 **집행 순서만** 바꾸지만, **`r`의 분모가 달라지므로 개봉 전 선언이 필요하다**
→ 3단계 결정 B.

#### (4) `registerStatus` 결측 — **§8.1의 전제가 2005–2025 창에서는 성립하지 않는다**

| 표본 | 분포 |
|---|---|
| H10B · 2005–2025 · 100건 | 소멸 63 · 취하 33 · **거절 4** · **`<EMPTY>` 0** |
| H01L · 창 없음(1955–1983 구간) 60건 | 소멸 44 · 취하 7 · 포기 3 · 거절 3 · `<EMPTY>` 3 (5.0 %) |

→ §8.1은 "`registerStatus`가 비어 있는 경우가 많아 거절 여부를 서지상세로 확정해야 한다"를 총콜
산식의 전제로 삼았다. **2005–2025 창의 100건 표본에서 결측은 0이다.** 전제가 흔들리므로 서지상세
사전확정이 불필요해지고, 이것이 (3)과 함께 예산을 크게 낮춘다. **다만 표본 100건이므로 파일럿에서
전량 재확인하고, 결측 건은 서지상세로 확정한다**(결측을 "거절 아님"으로 처리하지 않는다).

### 2.6 3단계(설계)로 가져갈 결정 3건 🛑

| # | 결정 | 쟁점 |
|---|---|---|
| **A** | 동일 출원일 타이 블록의 2차 정렬 | 서버는 출원일까지만 정렬한다. 클라이언트가 출원번호로 재정렬하되, **타이 블록이 페이지 경계를 걸칠 때** 블록 전체를 확보한 뒤에야 순서를 확정할 수 있다(경계에서 다음 페이지를 선취). 이 규칙을 명문화해야 결정성이 성립한다 |
| **B** | 검색 단계 사전선별 도입에 따른 **`r`의 재정의** | 사전선별 후 서지상세를 걸면 `r` = "서지상세 1콜당 (인용≥1 ∧ claim1) 통과율"이 된다. §1의 `r` 정의와 §8.1 산식(`200/r + 200`)은 유효하나 **분모의 모집단이 다르다.** 개봉 전에 정의를 고쳐 쓰고, 검색콜·서지상세콜을 각각 보고할지 결정 |
| **C** | 21 IPC 스트림 합병 방식 | ⓐ IPC별로 페이지를 받아 클라이언트에서 k-way 합병(전역 순서 정확 · 메모리 상주) ⓑ IPC를 순회하며 각각 앞에서부터(구현 단순 · **전역 순서가 깨져 §3 위반**). ⓐ가 §3을 만족하는 유일한 방식으로 보이나 명시 승인 필요 |

### 2.4 아직 확인하지 않은 것 (2단계에서 열어야 함) — **§2.5로 전부 해소됨**

- 검색 API가 `(출원일, 출원번호)` **정렬을 서버측에서 지원하는가.** 미지원이면 페이지를 전량
  받아 클라이언트에서 정렬해야 하고, 그러면 "앞에서부터"의 정의가 **수집 시점의 검색 결과 집합**에
  의존한다 — 결정성 문서화가 필요하다. **이것이 이 계획의 최대 미해결 위험이다.**
- 21종 IPC × 2005–2025 검색식이 반환하는 **모집단 크기**. 이것이 `r`의 해석을 좌우한다.
- `registerStatus`가 검색 응답에서 비는 비율(§8.1의 `r` 추정 전제).

### 8.2 BigQuery 배선 결함과 정정 (dry-run 이 잡았다)

dry-run 실측: **스캔은 쿼리당 5.22 GB 고정이고 `IN UNNEST(@apps)` 파라미터 개수와 무관**하다
(1·100·1,000·10,000건 전부 동일 · `WHERE` 없는 KR 전량 덤프도 동일). 그런데 `driver.main()` 의
배선이 후보 1건마다 `resolve_families([app])` 를 불러 **`family.py` 가 명시한 "배치 1회" 규약을
배선이 깨고 있었다** — 파일럿에서 최소 ~500회(≈$17), 상한 없음(BQ 에는 예산 계정이 없다).

정정(승인 후 실행): `family.load_kr_family_map()` 신설 — KR 전량 `(bq_app, MIN(family_id))` 를
1회 적재해 `data/interim/kr_family_map.parquet`(4,878,954행)로 캐시하고 `resolve_from_map()` 으로
조회한다. 사전순 최소 dedup 은 서버 `MIN()` 으로 집행되어 **규약이 같다**. `resolve_families()` ·
`build_family_map()` 은 불변. **총 BQ 비용 $0.0326 고정.**
규칙 불변 검증: A층 1,000건 재조회 결과가 `split.parquet` 과 **998 일치 · 불일치 0 · 미조인 2**
(= §5.0 의 fallback-self 2건). 회귀 테스트 `test_t5b_map_lookup_matches_resolve_semantics` 추가.

### 8.3 관측된 결함 1건 — `dup_within_b` 가 원장에 남지 않는다 (**수치 불변**)

원장 4,331행의 고유 출원번호가 4,281로 **`dup_within_b` 행이 0건**이다. 그러나 실제로는 중복이
있었다 — 캐시 대조 결과 `1020050000048` 은 H01L·H10D·H10W **3개 스트림의 응답에 모두 들어 있다**
(동결 21종 중 2개 이상을 가진 원장 행이 801건).

원인: `driver.run()` 의 재개 가드(`if rec.application_number in state.seen_applications: continue`,
`driver.py:196`)가 합병기의 `dup` 플래그 처리보다 **앞에** 서서, 중복 사본이 `screen_free(...,
is_duplicate=True)` 에 닿기 전에 걸러진다. T3 는 `merged_with_dups` 를 **단위로만** 검사해
이 경로를 보지 못했다.

**영향 범위 — 판정과 수치는 바뀌지 않는다.** dedup 자체는 정상이고(출원번호당 1행·1판정),
`r`·`r_free`·`r_family` 의 분모는 **고유 후보**여서 §5.7 정의 그대로다. 잃은 것은 §5.4 가 남기려던
**중복 발생 건수의 기록**뿐이다. 따라서 파일럿 결과는 재산출하지 않는다.
**미조치로 남긴다** — 고치면 원장 스키마의 행 구성이 바뀌므로 §3.1 착수 전 별도 승인 대상이다.

### 8.4 사전등록 대비 유의할 관측 (완화 아님 · 보고 의무)

- **채택 200건이 전부 2005-01-03 ~ 2005-02-28 출원**이다. §3의 "출원일 오름차순 앞에서부터"의
  직접 귀결이며 규칙대로다. 그러나 A층(1997–2025)과 시기 분포가 근본적으로 다르므로
  **A층 test 결과와 직접 비교하지 않는다**(프로파일 §3.3 이 같은 경고를 싣는다).
- 주분류가 `G02F` 52 · `H01J` 36 · `H10P` 22 에 몰렸다 — A층 상위(`C23C`·`H10B`·`H10P`)와 다르다.
  A층 주분류 대조표는 여전히 붙이지 못한다(상류 원본에만 있다 · CLAUDE §0.1 · §7.2 항목 4).

  4.88 M 건이라 2005년 출원의 미조인이 없었고, A층 959 패밀리와도 겹치지 않았다.
