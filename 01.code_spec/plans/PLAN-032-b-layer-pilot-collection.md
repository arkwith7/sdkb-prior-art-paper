## 0. 결론 먼저 — 기존 스크립트로는 §3을 집행할 수 없다

PLAN-031 §1은 수집 도구로 `~/Dev/paper_data/scripts/expand_dataset_via_api.py`(3,153줄)를 지정했다.
**그 지정은 유효하지만, 그대로는 §3을 만족시키지 못한다.** 실측(§2)에서 세 가지가 확인됐다.

| §3 요구 | 기존 스크립트 | 판정 |
|---|---|---|
| 표집 순서 = `(출원일, 출원번호)` 오름차순 | **없음.** 전략(stage 1–4)·키워드 게이트 순으로 페이지를 훑는다 | **미구현** |
| IPC 주분류 ∈ 동결 21종 | `ipcNumber`는 **검색식의 필드**일 뿐 주분류 필터가 아니다 | **미구현** |
| 기존 1,000건과 패밀리 서로소 | `seen`은 **출원번호 집합**뿐. 패밀리 개념 없음(`process_family`는 공정 라벨) | **미구현** |
| 거절 · 인용≥1 · claim1 | 사전/사후 필터로 **구현돼 있음**(`examinerQuotationFlag='Y'` · `claimInfoArray`) | 재사용 |
| 호출 1회로 IPC+claim1+인용 동시 취득 | `getBibliographyDetailInfoSearch` 1콜 — **구현돼 있음** | 재사용 |
| 원자적 append·중단 복구 | JSONL 1건씩 append — **구현돼 있음** | 재사용 |

**따라서 요구는 "스크립트 실행"이 아니라 "§3 집행 드라이버 신설 + 기존 스크립트의 호출·파싱 계층
재사용"이다.** 이것이 이 요구정의가 필요한 이유다. 기존 스크립트를 §3에 맞게 개조하는 선택지는
**택하지 않는다** — 그 파일은 A층 1,000건을 만든 산출물이고, 고치면 A층의 재현 좌표가 흔들린다.

## 2. 분석 — 실측된 사실 (CLAUDE §2-2 · 가정은 "가정"으로 라벨)

### 2.1 API 키 프로필 — **paid 급으로 확정. free 아님**

| 증거 | 값 |
|---|---|
| `paper_data/data/processed/collect_phase_b_kr.log` 말미 | `used={'kr': 3470, ...} quota_hit=False` |
| `paper_data/data/processed/backfill_admin_docs.log` 말미 | `used=693, quota_hit=False` (예산 캡 800) |
| 스크립트 프로필 정의(`expand_dataset_via_api.py:95`) | free = 150/일 · paid = 600/일 |

**단일 실행에서 3,470콜이 quota 오류 없이 완주**했으므로 이 키는 150/일 플랜이 아니다.
→ **파일럿 500콜은 하루 안에 소화된다.** 다만 이는 *과거 관측*이고 계약 잔여량의 증거는 아니다 —
파일럿 실행 시 `quota_hit` 을 로그에 남겨 **당일 실측으로 재확인**한다(가정 아님, 관측으로 승격).

### 2.2 배제기준 1(패밀리 서로소)의 집행 경로 — **`family_pub_numbers`를 쓰면 안 된다**

PLAN-031 §3 배제 1은 "`family_pub_numbers` 또는 `simple_family_id` 교집합"이라 적었으나, 실측:

- `rejected_patents_meta.parquet`(1,000행 38열)에 **`simple_family_id` 열은 없다.**
- `family_pub_numbers`는 str이며 내용이 **우선권·PCT 출원번호**다 — 예: `PCT/US2021/019245|62/982,956`.
  DOCDB 패밀리 공개번호가 아니다. 토큰 1,411개 중 고유 1,270개 · 보유 행당 평균 2.64개.
- **`has_family = False`가 466/1,000 (46.6 %)** — 절반 가까이가 이 열로는 비교조차 되지 않는다.

**따라서 이 열로 §3 배제 1을 집행하면 기준이 절반만 작동한다.** 대신 이미 있는 정본 경로를 쓴다:
`collect/bq_family_ir`(BigQuery DOCDB) — IR 코퍼스 40,552 문서 **결측 0**, 조인율 **95.8 %**
(docdb-app 89.2 % · docdb-pub 6.6 % · fallback-self 4.2 % = 자기 자신을 패밀리로)
(`data/profiles/ir_family_map.md`).

> **이것은 사전등록의 변경이 아니라 결함의 정정이다.** §3의 *규칙*("기존 1,000건과 동일 패밀리 배제")은
> 그대로이고, 규칙이 지목한 *필드*가 그 규칙을 담고 있지 않았을 뿐이다. 규칙을 느슨하게 만드는
> 방향이 아니라 **더 엄격하게 집행하는** 방향의 정정이므로 §1-2에 저촉되지 않는다.
> 승인되면 PLAN-031 §3 배제 1의 문구를 "DOCDB simple family(`bq_family_ir`) 교집합 ≠ ∅"로
> 정정하고, **정정 사실과 사유를 §8에 남긴다.**
> **미결:** fallback-self 4.2 %는 패밀리 판정 불능이다. 이 건들을 ⓐ 보수적으로 배제할지
> ⓑ 출원번호 일치만으로 판정할지 **개봉 전에 정해야 한다**(§3 설계 단계 결정 사항).

### 2.3 A층 실측 — B층 분포 대조의 기준선 (§4 보고 의무 입력)

- 출원일 범위 **1997-12-31 ~ 2025-04-22** (2005 미만 9건 = PLAN-031 §3 기재와 일치)
- 주분류 상위: `C23C` 215 · `H10B` 196 · `H10P` 142 · `H01L` 88 · `H10D` 74
- `has_family` True 534 / False 466

### 2.4 아직 확인하지 않은 것 (2단계에서 열어야 함)

- 검색 API가 `(출원일, 출원번호)` **정렬을 서버측에서 지원하는가.** 미지원이면 페이지를 전량
  받아 클라이언트에서 정렬해야 하고, 그러면 "앞에서부터"의 정의가 **수집 시점의 검색 결과 집합**에
  의존한다 — 결정성 문서화가 필요하다. **이것이 이 계획의 최대 미해결 위험이다.**
- 21종 IPC × 2005–2025 검색식이 반환하는 **모집단 크기**. 이것이 `r`의 해석을 좌우한다.
- `registerStatus`가 검색 응답에서 비는 비율(§8.1의 `r` 추정 전제).

## 3. 성공/실패의 사전 정의 (결과를 본 뒤 바꾸지 않는다)

- **`r` 실측 후 예산 확정**은 자동이다: 총콜 ≈ `200/r + 200`. `r`을 본 뒤 200건 목표를 낮추지 않는다.
- **파일럿에서 `r`이 매우 낮아도(< 3 %) 기준을 완화하지 않는다.** PLAN-031 §3 정지 규칙대로
  확보 N으로 진행하고 검정력을 재계산해 **개봉 전** 보고한다.
- 파일럿 500콜의 채택분은 **버리지 않는다** — §3 표집 순서를 따르므로 본수집의 앞부분이다.
